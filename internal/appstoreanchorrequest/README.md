# Canonical anchor request plans

This isolated package prepares proposed-v1 bytes from `docs/application-store/IO.md`; it never sends them. `NewRead` emits exactly 48 bytes with caller-supplied nonzero store/request IDs. The caller remains responsible for cryptographically fresh Read IDs and outstanding-request collision handling. This package performs no randomness, network, credential, file, journal, CAS, KDF, encryption or retry operation.

`NewCreate` emits exactly 272 bytes for canonical genesis. Its key is `SHA256("SSAPP-CREATE-v1" || store_id || state192)` and its request ID is the first 16 bytes of `SHA256("SSAPP-CREATE-REQUEST-ID-v1" || store_id || key)`. This does not establish that the store is absent or authorize creation/reset.

`PlanReservation` requires an admitted predecessor and an Entry whose index equals the current journal count below 2^20. It advances only count/head and preserves sequence/committed tuple. IDs matching the current committed snapshot or transaction reject, but full anchored/retained-history freshness is NOT checked. The key is `SHA256("SSAPP-RESERVE-v1" || store_id || entry40)`; its ID uses `SSAPP-RESERVE-REQUEST-ID-v1` with store/key as above. The 304-byte CAS contains the exact predecessor state hash and proposed state. It does not append/sync the journal or confirm reservation.

`PlanCommit` accepts only a private reservation-plan value and a nonzero candidate-file hash. It fixes snapshot/transaction IDs to that entry, advances sequence once, and preserves reservation count/head. Its key is `SHA256("SSAPP-COMMIT-v1" || store_id || txn_id || candidate_hash)`; its ID uses `SSAPP-COMMIT-REQUEST-ID-v1`. The CAS expects exactly the proposed reservation state. No domains add NUL separators. Zero derived keys/IDs reject without random replacement.

Request bytes, states, hashes and IDs are copy-safe. The zero Request is invalid; errors return it without partial metadata. `Valid` means a byte plan only. The planner has no service enrollment, authenticated transport, actual authoritative state, exclusive ownership, complete history, durable recovery copy, verified immutable candidate or fsynced intent. It does not enforce single use across copied values or know whether encryption/CAS has happened. It must never be used to re-encrypt, reparent or synthesize a replacement CAS for an old candidate after uncertainty.

Rebuilding from identical input recreates the same bytes/IDs/key. Changing inputs is not a retry. The protocol's key formula does not include every predecessor field: the same entry/store can produce the same key/request ID with different canonical CAS bytes. The service's durable per-credential canonical-mutation binding MUST reject that conflict as an integrity error; never substitute a new key/ID. Tests include this explicit witness. On unknown outcomes, a future orchestrator must authenticate Read first, compare exact expected/new tuples, and replay only the independently durable original request/intent under the specified service replay rules. No automatic recovery is implemented here.

## Commit-intent bytes

`NewIntent` accepts only a private commit-plan Request and emits exactly 312 bytes: `SSAPCMT1 || txn_id[16] || expected_state_hash[32] || new_state[192] || idempotency_key[32] || candidate_file_hash[32]`. `ParseIntent` requires exact length/magic/store scope, nonzero expected hash and a positive committed state. It checks transaction/candidate equality with that state, the exact commit key, and rejects a no-op expected hash equal to the new state hash. It reconstructs the same canonical 304-byte CAS and deterministic request ID without selecting another predecessor, location, key or candidate.

Intent bytes are unkeyed metadata, not proof that an immutable record existed or was fsynced. The constructor writes nothing. A parser can accept a deliberately manufactured self-consistent record; trusted directory/ownership, exclusive no-follow creation, file/directory durability, reopen/byte comparison, verified candidate hash/tags/sidecar and authoritative journal/anchor checks remain mandatory. The expected state hash alone cannot prove the predecessor transition. `Intent.Valid` and `Intent.Request` do not authorize replay. Never synthesize an intent for an old candidate on restart; load only the independently established original record, then perform authenticated read-first reconciliation. Errors return zero Intent with no partial Request; bytes and reconstructed values are copies.

Independent byte/hash/ID vectors cover all operations, exact intent/CAS reconstruction, deterministic rebuilds, transition field preservation, current-ID reuse, invalid/cross-kind plans, final reservation boundary, ownership and canonical-binding collisions. Tests were authored but not executed locally; public GitHub CI supplies execution evidence. Local work ran formatting only. Production MCP remains deny-only; SSH and four independent 1-GiB Argon2id/1000 AES layers are unchanged.
