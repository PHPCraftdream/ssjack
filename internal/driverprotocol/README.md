# Driver protocol structural checks and pinned schemas

`internal/driverprotocol` provides structural request/response checks, frame I/O, and opt-in validation against caller-supplied pinned schemas. Structural success alone does not establish enrolled/runtime schema conformity, semantic validity, authorization, safe execution, or policy acceptability. This package is not integrated with driver execution; callers supply identities/documents and remain responsible for enrollment resolution and authorization.

Parsing requires valid UTF-8 and NFC strings and keys, rejecting C0/C1 controls (U+0000–U+001F and U+007F–U+009F), unpaired surrogate escapes, duplicate decoded keys, floats, unsafe integers, excess depth/nodes/container sizes, extra JSON values, and extra bytes after a frame. Valid surrogate pairs and U+FFFD are accepted. Frame writing checks bounded generic JSON only; it does not validate request/response shapes. Frame readers require EOF, so writers must be closed and deadlines enforced by callers.

Pinned schema validation uses a strict subset of the Draft 2020-12 dialect: root `$schema` must be `https://json-schema.org/draft/2020-12/schema`; supported keywords are `type`, `enum`, `const`, annotations `title`, `description`, `default`, `examples`, and type-applicable `properties`, `required`, `additionalProperties`, `items`, `minItems`, `maxItems`, `minLength`, `maxLength`, `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, and `multipleOf`. All other keywords reject, including `$schema` below root. Objects are closed and all listed properties are required. Arrays require bounded `maxItems` and a valid `items` schema, except that `items` may be omitted when `maxItems` is exactly zero; present `items` is always validated. Type arrays support exactly one supported non-null type and `null`, in either order. Strings require bounded `maxLength`; only safe integer bounds and positive safe integer divisors are supported. String lengths count Unicode scalar values; strings and keys must be NFC. `title` and `description` must be strings; `default` may be any bounded JSON value and `examples` must be an array of bounded JSON values. These annotations are validated at every schema node, including nullable nodes, but do not constrain values, supply defaults, or grant authority. They remain in the canonical document and affect its digest. Unsupported features include references, patterns, formats, `uniqueItems`, tuples, and arbitrary additional properties. This is not full JSON Schema or v1 protocol conformance.

Schema input is bounded to 262144 raw bytes and 65536 JCS-SSJACK-1 canonical bytes; depth, node and container limits remain enforced. Schema digests and desired/projection byte accounting use shared JCS-SSJACK-1 canonical UTF-8 encoding, including literal `<`, `>`, `&`, U+2028 and U+2029. No schema lookup, runtime execution, authorization, or MCP integration is performed.

`ValidatePinnedValue` accepts raw pinned schema bytes, expected schema ID/digest, actual target/kind/schema ID, and raw value bytes. It parses both with `ParseJSON`, applies structural bounds, computes the `ssjack-schema-v1\0` digest, and only then validates the value. `ValidatePinnedProjection` checks the request schema ID against the correlated structural request and separately pins the projection document/digest; desired and projection IDs may differ as specified by Kind enrollment. `ValidatePinnedRequest` accepts only plan/apply; use structural validation for other actions, which does not claim schema validity. Callers provide the enrolled identity/document; these helpers do not resolve enrollment or authorize it. This deliberately partial subset is not v1 conformance or full Draft 2020-12. `uniqueItems`, references, patterns, formats, and other unsupported keywords are rejected. No automatic schema lookup, execution, authorization, or MCP integration is performed.
