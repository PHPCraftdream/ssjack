# Internal recovery state machine

`internal/recovery` is standalone, not integrated with Open or production anchor code. The caller provides Anchor and Journal. Binding fixes initialization/reservation/invocation stage, invocation/resource, transaction ID, exact old/new generation+hash tuples, and request hash. IDs, including nonempty transaction IDs, are 1–128 bytes of printable ASCII (`0x21`–`0x7e`). Genesis is exactly generation 0 with an empty expected transaction; every later expected generation requires a nonempty expected transaction. Expected transaction must differ from the binding transaction. Next carries the binding transaction.

The transaction ID is assumed to uniquely commit the entire binding (stage, invocation, resource, expected/next tuples, request hash). The trusted anchor adapter must enforce one immutable transaction-ID-to-full-binding mapping, or the ID must be cryptographically derived from that binding; this package neither computes nor verifies that commitment. CAS receives `Binding.Transaction` (not invocation) as its transaction key.

The caller—not Journal—must hold exclusive serialization for invocation and resource from before LoadIntent through return, including any conflicting stored resource. QuarantineConflict must atomically preserve the original intent evidence and durably block both bindings; nil is guaranteed only after both blocks. If it errors, either outcome is unknown and the caller must maintain a global admission fence until external linearizable reconciliation proves both blocked; the error itself does not mean a durable block. Journal mutations are atomic and conditional: nil from PutIntent means exactly Prepared is durable; nil from SetPhase means Prepared→Committed durably occurred or Committed was confirmed; nil from Quarantine means both identities are blocked.

Invocation/resource quarantine blocks both identities. A conflicting stored/requested binding is handled by one atomic QuarantineConflict operation: it preserves the original binding as evidence while blocking both resources and invocations. If it returns an error, no permanent block is implied; global admission remains fenced pending external reconciliation. Invocation-stage intents are never executed; recovery quarantines them. Existing prepared initialization/reservation records with the old anchor tuple are unavailable and never re-CASed. Anchor reads are authenticated and linearizable. CAS compares the complete old tuple (resource, generation, hash, transaction), advances atomically to the complete new tuple, is monotonic by generation, and cannot overwrite a newer/conflicting state. Nil means the exact new tuple is durable. An uncertain CAS must never apply after a subsequent linearizable Read returns; otherwise the protocol is unsafe. Recovery success requires durable Committed and a final read of the exact Next tuple. Committed rollback is quarantined. This protocol does not protect against compromised components or journal/host rollback; no production durability implementation is included. Tests are synthetic; not run locally.

## Recovery journal limitations

The Linux-only journal stores at most seven records (64 KiB), with at most two blocked bindings per quarantined record. Each publication creates, writes, syncs, and closes a `.pending` marker, then syncs the journal directory; it writes, syncs, and closes `.new`, renames it over the journal, syncs the directory, removes `.pending`, and syncs the directory again. Live reads reject either `.pending` or `.new`, poisoning the instance. The journal refuses reopening an existing journal directory; there is no verified reopen/recovery path, automatic cleanup, or rollback. A crash or ambiguous I/O error can leave a marker or temporary file and requires external admission fencing; it must not be interpreted as permission to roll back or continue. The full ancestor directory chain must be trusted and not attacker-writable; this prototype does not use dirfd/openat2 protections and therefore cannot defend against path replacement races by a hostile ancestor. Durability depends on the filesystem, storage device, and hardware honoring file/directory `fsync` and atomic same-filesystem rename; those guarantees are not independently verified here. No authenticated anchor implementation exists, and this journal does not protect against filesystem/host rollback or tampering by an actor able to rewrite and recompute its unkeyed digest. Cross-process locking and complete fault-cut coverage remain limitations. Treat any uncertain I/O error as requiring external admission fencing; this journal is not production-qualified. No local tests/build/lint/typecheck were run.
