# Policy, canonicalization, and approval

Status: the deny-only installed subset described below is implemented; full policy evaluation remains proposed and not implemented. Exceptional approval is explicitly unavailable. No console, terminal, local account, UI, or model interaction authenticates a human approver.

## Policy and effects

Keeper-owned, immutable, human-installed policy scopes session mode, complete enrolled driver identity, target, principal, resource ID/kind/schema, policy revision, effect classes and canonical desired-value ranges. Default deny. Only bounded `delegated` effects may execute. `observe` is mandatory/read-only; `approval_required` permits read-only observe/planning but never executable apply. Destructive effects, identity/enrollment/policy changes, exceptional recovery, and unknown effects are denied. Agent/client cannot edit policy or capabilities. Backend and OS permissions independently enforce scope. Any bound policy/identity change invalidates plans.

`RuntimeEffect` is exactly `{class,summary_id,destructive}`. `PolicyEffect` is separately `{class,decision,destructive,summary_id}`, where decision is `delegated|approval_required`; never conflate or forward it as a `RuntimeEffect`. Validate each effect before plan persistence and again before apply. Sort class, then summary_id by Unicode scalar sequence, then destructive false before true; reject duplicates and unsorted lists. Empty effects retain the plan; apply reserves a durable operation and succeeds unchanged only after a fresh read-only observe confirms exact desired outcome and plan precondition. It never invokes mutation or fabricates revision. If confirmation is unavailable or uncertain, refuse/report uncertainty.

## Canonical values and binding

Proposed v1 `JCS-SSJACK-1` (not RFC 8785) requires strict UTF-8 JSON; reject duplicate decoded object keys, non-NFC strings and keys, lone surrogates, floats/non-finite numbers, unknown fields and invalid schemas. Strings and keys must consist of Unicode scalar values and must not contain U+0000–U+001F or U+007F–U+009F, even when escaped. Valid surrogate-pair escapes decode to a scalar; they are not canonical output. Sort object keys by Unicode scalar sequence, preserve array order, emit no whitespace, use shortest base-10 integers and lowercase booleans/null.

For every string and key, emit a double-quote delimiter, then literal UTF-8 for each allowed scalar except U+0022 and U+005C, then a double-quote delimiter. Encode U+0022 only as `\"` and U+005C only as `\\`. In particular, U+2028 and U+2029 are literal UTF-8 (bytes `e2 80 a8` and `e2 80 a9`), not escapes. Do not escape `/`, `<`, `>`, `&`, or other allowed scalars. Alternate valid JSON spellings may be accepted as input but are not canonical bytes.

Examples (each code span is complete JSON): `"a\"b\\c/<> &"` is canonical; `"a\u0022b\u005cc\/\u003c\u003e \u0026"` represents the same string but is noncanonical. `"é"` is canonical UTF-8 (`22 c3 a9 22`); `"\u00e9"` is noncanonical, while decomposed `"e\u0301"` is rejected as non-NFC. A string containing only U+2028 has canonical bytes `22 e2 80 a8 22`; `"\u2028"` is noncanonical. U+2029 likewise has canonical bytes `22 e2 80 a9 22`; `"\u2029"` is noncanonical. `"\n"` and `"\u0085"` are rejected controls, not alternative encodings. `{"a":1,"\u0061":2}` is rejected for duplicate decoded keys.

Domains: schema `ssjack-schema-v1`, tool pair `ssjack-tool-schema-v1`, plan `ssjack-plan-v1`, enrollment `ssjack-enrollment-v1`, desired `ssjack-desired-v1`, effects `ssjack-effects-v1`; SHA-256(ASCII domain + NUL + canonical bytes), lowercase hex.

The isolated `internal/domaindigest` prerequisite canonicalizes JSON using the existing bounded `canonicaljson` implementation and computes these six digests. It is not wired into the runtime, does not validate schemas, sort or validate effects, enforce purpose-specific limits, authenticate data, or authorize operations. Callers must perform those checks independently. It does not change the raw-byte digest of the installed policy subset below.

`plan_binding` is a closed exact object binding the canonical target/resource pair; `enrollment_digest`; driver identity/protocol and code, dependency, configuration, and artifact digests; the enrolled `principal` object `{issuer,subject}`; policy revision; kind and the desired/projection schema ID+digest pairs; canonical desired value; exact effects; precondition; and creation/expiry timestamps. Its fields are exactly `{protocol,plan_id,session_id,declaration,target,resource_id,canonical_target,canonical_resource,driver_id,driver_protocol,code_digest,dependency_digests,configuration_digest,artifact_digests,principal,kind,schema_id,schema_digest,policy_revision,precondition,desired_schema_id,desired_schema_digest,desired,effects,effect_digest,projection_schema_id,projection_schema_digest,enrollment_digest,created_at,expires_at}`. `canonical_target` and `canonical_resource` are `ResourceId` values from the unique enrolled alias mapping and are the interlock key; `target` and `resource_id` retain the accepted declaration labels. `schema_id` and `schema_digest` equal the desired schema pair, not a third schema. `protocol` is integer 1; plan/session IDs are `Id`, driver ID/kind/schema IDs are `Name`, driver protocol is integer 1, policy revision is `Revision`, digest maps and principal have the enrollment types, effects are `RuntimeEffect[]`, and precondition is `Revision|null`. `declaration` is exactly `{kind,schema_id,schema_digest,resource_id,target}` and has no desired; desired is separately present and validated by its schema pair. No `effect_schema_id` or `effect_schema_digest` exists: effects are exact typed values with the domain-separated `effect_digest`. Equality is exact canonical-object equality. Schema documents are never embedded in plan DTO. `effect_digest` uses `ssjack-effects-v1\0` over canonical sorted effects. Digests are lowercase 64-hex. Timestamps UTC `YYYY-MM-DDTHH:mm:ss.SSSZ`; IDs follow protocol grammar. No omitted, extra or opaque fields. All text is NFC; no title/description/default/example annotations or other non-contract metadata may occur in common hashed schema documents. External schema documents may contain the annotations allowed by schemas.md; they have no contract authority. A schema root has only `$schema` plus its defined schema keywords; never add recursive metaschema machinery.

## Implemented deny-only installed subset

The current runtime implements only a non-authorizing `ssjack-policy-subset-v1` snapshot. Exact closed JSON fields: `format` (that exact string), `enrollment_id` (canonical 16-byte unpadded base64url), `driver_id` (Name grammar), `driver_protocol` (integer 1), and `revision` (Revision grammar `[A-Za-z0-9._:-]{1,128}`). All fields required, no nulls, duplicate decoded keys (including keys written with escaped JSON characters), unknown keys, trailing JSON, invalid UTF-8/JSON, or files over 4096 bytes. JSON escapes are accepted if valid; `encoding/json` replaces lone surrogate escapes with U+FFFD, which is rejected by the ASCII-only `Name`/`Revision` grammars (and identity matching). Digest is SHA-256 of exact raw input bytes (raw byte identity), not a JCS or v1 canonical digest. The human launcher selects it with `--policy-snapshot ABSOLUTE_PATH`, together with `--mode declarative --enrollment-metadata ABSOLUTE_PATH`; policy identity must exactly match metadata. The keeper captures the validated value before launch/attachment; descriptor protocol `ssjack-policy-deny-only-1` exposes revision and SHA-256 snapshot digest solely as identity. Full mode cannot accept it. All operations except descriptor discovery deny; registry/tools remain empty. This is not policy evaluation, authorization, approval, a mutable configuration channel, or a model-controlled file/path. No SSH/vault policy behavior is changed. This subset does not implement effect scopes, policy editing/install UI, revocation, authenticated distribution, or any positive authority. Human file selection is not proof of human identity.
## Approval

Exceptional approval is unavailable in v1 without exception. `approval_required` returns `APPROVAL_REQUIRED` and permits read-only observe/planning, but creates no executable plan; no apply is available. A plan that would require any approval is non-executable. No approval endpoint, token, recovery credential, identity proof or protocol exists. Future approval requires separate human product/security decision, independently authenticated approval, durable revocation, exact plan/effect/session/target binding, expiry, audit and atomic one-use reservation. OS prompts, TTY, process identity, MCP prompts, `confirm:true`, UI clicks or typed phrases are not human identity.
