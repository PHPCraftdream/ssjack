# Operation lifecycle and durability

Status: proposed v1; not implemented. Keeper persistence is authoritative, not response delivery. This specifies planning/execution boundaries, not reconnect, authentication, or approval.

## Resource identity and interlock

Each operation binds to a stable canonical target/resource pair established independently of session, attachment, alias, driver, or caller label. Human-enrolled, immutable identity is persisted with plan/operation. Resolve aliases before lookup; aliases never create distinct resources/interlocks. Persist one interlock per canonical pair; re-enrollment, new driver, changed code/dependencies/config, session, or alias cannot bypass it. If equivalence is uncertain, treat as potentially same resource and quarantine broadest defensible scope; deny unproven aliases.

Quarantine is durable, resource-scoped, fail-closed. It denies model/client reads, execution planning and automated work while retaining evidence. Unknown/ambiguous outcomes remain quarantined by default. Only human review with affirmative evidence of safe state and no duplication/conflict may clear it; a fresh authorized launcher process then establishes recovery. Silence, timeout, process exit, new enrollment/session, or driver assertion alone is not proof. Safe state is not operation approval. Unresolved scope quarantines enrollment/session; attachment loss alone does not broaden to unrelated resources.

## Lifecycle

1. Human enrolls driver, code/dependency closure, configuration, schema, principal, OS identity, target, artifacts, sink and policy out of band; verify immutable identities.
2. Bridge authenticates once; keeper fixes declarative mode/tool set. No full-operation fallback.
3. `driver_list` reports exactly `driver_id`, `protocol`, `kinds`, `capabilities` and `limits`. It reports no schema documents, IDs or digests. A human provides the allowed schema IDs; the keeper validates the enrolled Kind and `SchemaEntry`. `resource_status` performs bounded read-only observation and reports safe projection/revision.
4. `resource_plan` receives desired and request ID; keeper observes current state/revision and stores immutable plan. `plan_apply` accepts only plan ID/request ID; keeper loads stored binding. Plan reserves at most one operation and is never reusable. Repeated plan/request returns original result or conflicts; never creates another operation.
5. For non-empty plan, validate expiry, bindings, policy, OS/driver identity and preconditions before reservation. `approval_required` denies executable apply. Reject stale/uncertain checks without invocation. Reserve durably before invocation; require exact backend CAS or independently enforced exclusive ownership. Empty effects also reserve durable operation and never invoke driver apply.
6. A fresh no-op observation must confirm the desired projection and the plan's expected revision. The revision check must be independently enforced through exclusive ownership or an atomic backend observation/revision check at the recorded observation linearization point. A null revision is permitted only under independently enforced exclusive ownership. No-op success proves this observation only; it does not claim permanent convergence.
7. Validate response and durably commit before reply. Applied, delivered, observed and adopted revisions are independent evidence and are exact revisions or null when unsupported. For a successful no-op, `applied:null`, `delivered:null`, `adopted:null`, `observed` is the actual fresh revision (null only under independently enforced exclusive ownership), and result is `{"verified":true,"projection":<fresh observed desired projection>}`. `verified` is true only when the projection was observed to equal desired. V1 has no secret delivery; delivered/adopted secret null. Adoption requires enrolled evidence.

## States, evidence, cancellation

Plan: `PLANNED -> INVALIDATED | EXPIRED | RESERVED`. Bind desired, desired/projection schema identities/digests, canonical target/resource, enrollment/driver identities, policy revision, observed revision, exact effects and timestamps. Any mismatch invalidates.

Operation: `RESERVED -> RUNNING -> SUCCEEDED | FAILED | CANCELLED | UNKNOWN`; `RESERVED -> SUCCEEDED | FAILED` legal for confirmed no-op or proven pre-invocation failure. UNKNOWN resolves only with explicit read-only reconciliation evidence and actual revision evidence (or explicit human-reviewed safe proof). No-op success needs fresh observation confirming desired projection and expected revision under the independently enforced check described above. Revocation invalidates queued plans, prevents not-started work, requests cancellation for started local work, blocks reads/continuation, and quarantines. Never expose quarantined data to models.

Persist reservation with owner session, immutable plan/digest, request key, canonical resource and operation ID before effects. Persist invocation-start marker before launch. Before-marker failure is FAILED only with proof of no effect; after-marker crash is UNKNOWN, never auto-retried. FAILED requires proof of no effect or deterministic final failure. SUCCEEDED requires contract evidence; missing required verification means UNKNOWN. Process exit alone proves neither. Possible effect without durable outcome, including final commit failure, is OUTCOME_UNKNOWN and quarantined.

Cancellation is part of the original ordinary operation, not a new active ordinary operation. The first accepted intent records monotonic time `t`; its queue deadline is exactly `t + 10000ms`. Its execution deadline is `min(actual launch + 600000ms, original operation absolute deadline)`. Retries never extend either deadline. Queue expiry persists the accepted intent as pending and never auto-launches it; report unsupported only when the enrolled driver lacks the capability. Report outcomes truthfully as UNKNOWN and quarantine when remote effect is uncertain. Model cancellation of UNKNOWN is denied. A local stop never proves remote stop. Terminal SUCCEEDED/FAILED/CANCELLED operations never spawn cancellation work. Human recovery is separate from model cancellation.

For the current attached MCP/broker route, cancelling the caller context closes that client connection; the keeper handler runs under its session context and may continue. A cancelled in-flight call can therefore lose its reply after the external driver effect has committed. Do not infer rollback or retry the closed client. Reconciliation guarantees here are limited to the same live-session fitting route and do not establish remote cancellation. The task231 lost-reply fixture separately covers the internal driver deadline/read-first reconciliation path.

## Attachment, bounds, retention

One-use attachment cannot reconnect or be claimed twice. Same-live-session retries use durable idempotency. Disconnect/timeout/process loss consumes attachment; never retry possible mutation. Quarantine affected work; no model lookup, continuation, or new authentication/authorization attempt.

Limits: request 256 KiB; desired 32 KiB; projection 8 KiB; driver frame 64 KiB; schema depth 16/4096 nodes. Observe timeout 10 s, plan 30 s, apply/cancel/reconcile 600 s; operation deadline 3600 s. Idempotency key `(session_id,tool,request_id)`; request ID random 16-byte unpadded base64url. Persist canonical input digest/result; same key/digest returns original, changed digest CONFLICT.

Admission is bounded by configured enrollment and session limits. Per enrollment: at most four ordinary processes plus one cancellation process; distinct operations may use the four ordinary slots. For each original operation, prohibit parallel actions and duplicate invocations; the sole action-concurrency exception is that its apply and its one cancellation may coexist, never a duplicate invocation. At most 32 active ordinary operations per session; at most 64 active ordinary operations globally, including queued, running and unknown. Ordinary processes are capped at 64 globally. Emergency cancellation processes are capped at 16 globally. Total ordinary plus emergency processes are capped at 80. Caps include queued/running/unknown work as applicable; refuse admission before effects.

Per session, combined durable plans, operations, idempotency results and cancellation intents are limited to 16 MiB and 256 records. Reserve one 4096-byte cancellation record for each accepted operation; coalesced cancellation request IDs create no alias records. The first accepted intent's queue deadline is exactly `t + 10000ms`, and execution deadline is `min(actual launch + 600000ms, original operation absolute deadline)`; retries never extend either deadline. Queue expiry persists accepted pending and never auto-launches it. Report unsupported only when capability is absent; otherwise persist truthful outcome, UNKNOWN when uncertain, and quarantine. Capacity must be reserved before accepting a record; cap exhaustion is LIMIT_EXCEEDED and storage failure INTERNAL. Never claim an unaccepted intent; never evict active/unknown records. Evict only oldest terminal records after 30 days, idempotently; expiry cannot revive, retries resolve existing records before expiry checks, cleanup cannot remove a plan with a reserved operation. Thirty days is minimum retention, not guarantee after eligibility.

Persist canonical desired content in immutable plan/operation binding. Never persist raw process output, secrets or backend exception text. Keep stable codes, times, revisions and reviewed allowlisted projections (≤8 KiB); unknown/free-form output fails closed. Before reservation, persistence failure means no invocation. After invocation may start, timeout/disconnect/malformed response/lost acknowledgment/crash/storage failure yields UNKNOWN; never auto-retry mutation or infer safety. No raw driver strings, secrets or backend exceptions returned.

## Current implementation note

The filesystem-backed operation store provides idempotency reservations and fail-closed quarantine for conflicting canonical resources. Linux publication uses sync/rename operations; other platforms fail closed where rollback protection is unavailable. Identities are trimmed printable ASCII; raw invalid UTF-8 and escaped surrogate code units are rejected. `Open` intentionally always returns unavailable for an existing store: recovery/reopen is prohibited because local filesystem sync failures cannot prove which state survived. Initialization leaves a pending marker if parent sync fails; successful initialization clears it only after syncing the parent. If marker removal/final directory sync fails, the returned instance is poisoned and unusable, while later `Open` remains unavailable. This is a deliberate severe availability tradeoff: persisted reservations and quarantines cannot be resumed by a new process, and no recovery mechanism is implemented. Filesystem sync is not a guarantee against rollback or power-loss behavior. Syscall-wrapper traces assert call sequencing only; they do not prove hardware behavior or crash durability. The store is disconnected from runtime execution and does not authorize work.
