# Declarative session protocol v1 (proposed)

Status: proposed contract; not implemented. No transport is added. It uses the existing pinned-loopback-TLS broker, `wire.Request{operation:string,data?:string}`, and `wire.Reply{ok:bool,error?:string,data?:string}`. Request data and successful reply data are canonical Ktav strings, not embedded JSON objects. MCP JSON-RPC terminates at the bridge. See driver, lifecycle, policy, and schemas specifications.

## Attachment and descriptor

Existing one-use `Auth{version:int,session:string,token:string}` is unchanged and bound to one fixed mode; no reconnect. `session.describe` is first in either mode, request `{min_protocol:1,max_protocol:1}`. Descriptor mode is `full|declarative`; `both` is invalid. Full mode retains exactly eight legacy tools (`remote_targets`, `remote_exec`, `remote_read`, `remote_cancel`, `app_list`, `app_exec`, `app_read`, `app_cancel`); declarative mode has exactly six: `driver_list`, `resource_status`, `resource_plan`, `plan_apply`, `operation_read`, `operation_cancel`.

Descriptor is `{protocol,min_protocol,max_protocol,min_request_bytes,max_request_bytes,mode,session_id,tools}`; `protocol`, `min_protocol`, and `max_protocol` are all 1. Request `{min_protocol,max_protocol}` remains the negotiation range. Each tool is `{name,input_schema,output_schema,schema_id,schema_digest}`. The deterministic JSON Schema definitions, ID construction and digest rule are specified in schemas.md; no type AST is used. Tool IDs are `ssjack.tool.<name>.v1`. Desired/projection values validate against exact enrolled documents in addition to the common tool schema; effects validate against the fixed common `RuntimeEffect` shape and enrolled policy effects, with no enrolled effect schema. Failure to negotiate the requested protocol/mode is an explicit refusal; no automatic legacy downgrade or silent fallback is permitted. A separately selected full-mode session retains its existing compatibility behavior.

Each request has exact outer fields `operation:string` and optional `data:string`; reply has `ok:boolean`, optional `error:string`, optional `data:string`. Request data, including session.describe, is canonical Ktav; no-argument operations encode `{}`. Success has `ok=true` and canonical Ktav keeper result envelope `{result:<typed result>,error:null}`. Transport/protocol failure is `ok=false` with fixed safe error. Application failures have `{result:null,error:{code,message,retryable,operation_id}}`; `output_schema` describes only the bare typed success result, not the keeper envelope. The bridge unwraps the keeper success envelope, validates the bare result against `output_schema`, then maps it to an MCP tool result with JSON-serialized result in a text content item, `structuredContent` equal to the result, and `isError=false`. Application failures map to a text content item containing JSON of the fixed error object, `isError=true`, and no `structuredContent`; they are not validated against the success output schema. This mapping applies only to new declarative tools; full-mode tools and behavior are unchanged. SDK metadata is not forwarded to MCP clients. The `session.describe` response is not an MCP tool result. These bridge mappings describe MCP tool results, not another keeper reply or MCP JSON-RPC response. Never expose backend/driver text; operation_id is null unless reserved.


Fixed application codes/messages: `INVALID_REQUEST` / "Invalid request."; `UNSUPPORTED_PROTOCOL` / "Unsupported protocol."; `MODE_DENIED` / "Operation unavailable in this session mode."; `NOT_FOUND` / "Resource or operation not found."; `SCOPE_DENIED` / "Target is outside the enrolled scope."; `DRIVER_UNAVAILABLE` / "Enrolled driver unavailable."; `DRIVER_IDENTITY_CHANGED` / "Enrolled driver identity changed."; `SCHEMA_INVALID` / "Input does not match the enrolled schema."; `POLICY_DENIED` / "Operation denied by policy."; `APPROVAL_REQUIRED` / "Effect requires approval, which is unavailable."; `APPROVAL_INVALID` / "Approval is invalid."; `PLAN_EXPIRED` / "Plan expired."; `PLAN_STALE` / "Plan is stale."; `PRECONDITION_FAILED` / "Resource precondition failed."; `CONFLICT` / "Request conflicts with an existing operation."; `LIMIT_EXCEEDED` / "Configured limit exceeded."; `BUSY` / "Resource is busy."; `CANCELLED` / "Operation cancelled."; `OUTCOME_UNKNOWN` / "Operation outcome is unknown."; `BACKEND_FAILED` / "Backend operation failed."; `OUTPUT_REJECTED` / "Driver output rejected."; `INTERNAL` / "Internal error." Retryable only for BUSY and pre-reservation DRIVER_UNAVAILABLE. APPROVAL_INVALID is reserved and not emitted. Foreign identifiers are indistinguishable NOT_FOUND.

## Operations

All tool DTOs and constraints are specified by deterministic JSON Schemas in schemas.md. Requests/results: `driver_list {}` → `{drivers:[Driver]}`; `resource_status {target,driver_id,kind,schema_id,resource_id}` → `{state,revision|null,observed_at,projection}`; `resource_plan {target,driver_id,kind,schema_id,resource_id,desired,request_id}` → `{plan_id,digest,expires_at,effects,precondition|null}`; `plan_apply {plan_id,request_id}` → `{operation_id,state}`; `operation_read {operation_id}` → `{operation_id,state,phase,progress|null,revisions,result|null,error|null,updated_at}`; `operation_cancel {operation_id,request_id}` → `{operation_id,state,cancellation}`. All objects are closed; all fields required, with null where explicitly nullable. Desired/projection values validate against exact enrolled desired/projection schema documents; effects validate against the fixed `RuntimeEffect` shape and enrollment policy effects, never an enrolled effect schema.

`resource_plan` performs observe and caller supplies no revision. `plan_apply` uses only stored plan and request ID. Empty effects still reserve a durable operation and succeed unchanged only after fresh observe confirms exact desired outcome and either exclusive ownership or atomic revision/observation at its recorded linearization point; null revision is valid only with exclusive ownership. Approval-required effects permit read-only observe/plan but no executable plan. Mutating apply requires exact observed-revision CAS or independently enforced exclusive ownership. A successful `plan_apply` acknowledges acceptance, not completion; its returned state may be any valid `ApplyOut` state, and callers read completion with `operation_read`. State never implies adoption. Cancellation is durable intent, not proof remote work stopped; cancellation results distinguish pending, unsupported and confirmed, and canceling UNKNOWN is refused. Only the new declarative mode uses this contract; full mode is unchanged.

For an operation's first accepted cancellation intent, the queue deadline is monotonic time +10000ms. The execution deadline is the earlier of actual launch time +600000ms and the original operation deadline; retries never extend either deadline. If cancellation cannot launch before `queue_deadline`, persist `cancellation=pending` with the accepted intent and never auto-launch it. Report unsupported only when cancellation capability is absent. Cancellation applies to the original operation and does not create a new active operation. Preserve the 4096-byte cancellation reserve. Four ordinary process slots per enrollment remain available across different operations; for a given operation, at most one apply process plus one cancellation process may run as the sole exception, with no other parallelism for that operation. Refuse cancellation of an operation whose state is UNKNOWN; likewise, terminal SUCCEEDED, FAILED, or CANCELLED states do not spawn cancellation processes. Do not infer that remote work stopped; the original operation outcome remains truthful, possibly UNKNOWN and quarantined until resolved.




Times are UTC RFC3339 at millisecond precision (`YYYY-MM-DDTHH:mm:ss.SSSZ`); timestamps are never rounded or silently reduced to seconds.

Measure actual canonical UTF-8 bytes. Driver JSON frame payload ≤65536 bytes excluding four-byte prefix (complete ≤65540); desired ≤32768; projection ≤8192. Broker Ktav payload ≤262144 bytes excluding prefix. MCP request and complete descriptor ≤262144; reject before over-cap allocation and refuse oversized descriptor. Include envelope/escaping in limits. `wire.Write` enforces only broker bound.

Canonical ordering and duplicate rejection follow schemas.md; tools use defined order; semantically ordered arrays remain ordered. Limits precede effects. Four ordinary processes and one separate emergency cancellation process slot per enrollment; cancellation reserve 4096 bytes per operation. Active ordinary operations: 32/session and 64 globally (queued/running/unknown included). Ordinary processes: 64 globally; emergency cancellation processes: 16 globally; ordinary plus emergency processes: at most 80. There is no separate 256-active global cap. Storage is per session: 16 MiB and 256 combined records inclusive. IDs are 16 random bytes unpadded base64url. Names ASCII `[a-z][a-z0-9._-]{0,63}`; resource IDs `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}`; revisions `[A-Za-z0-9._:-]{1,128}`. No arbitrary endpoints, paths, code, or secrets.
