# Cryptographic profile

Proposal only; unimplemented and unaudited, pending independent review. App-store human passphrase is distinct from SSH authorization. Four independent random 32-byte salts are generated at genesis, nonzero/distinct, immutable for dedicated master and repeated in snapshots. Every snapshot has fresh random nonzero 16-byte snapshot_id and 12-byte nonce_base. Rotation creates new store_id/master/salts and requires full re-encryption.

Obtain passphrase only from a real human-controlled TTY with echo disabled; reject redirected/non-TTY input. Decode terminal input as strict UTF-8 scalar values; no normalization, reject NUL, remove only one submitted LF or CRLF terminator, preserve all other bytes; enforce 1..16384 bytes after encoding. For passphrase UI, examples must make whitespace semantics explicit without asking for a real secret: spaces are significant and preserved; no Unicode normalization is applied. Example labels may show synthetic `" two words "` with leading/trailing spaces retained, and composed `é` versus `e`+combining accent as distinct byte strings. Never display, log or prefill user-entered secrets. Threat model excludes compromised TTY/OS, same-UID process inspection, root, malware, memory dumps, swap and runtime copies; memory clearing is best effort only. `HKDF-SHA-256` is RFC5869 Extract-then-Expand; absent salt is 32 zero bytes for HMAC-SHA256; exact ASCII info; L=32. Sequentially compute `A_r=Argon2id-v1.3(passphrase_bytes,salt_r,m=1,048,576 KiB,t=1,p=1,out=32)`, r=0..3. `M=HKDF-SHA-256(IKM=A_0||A_1||A_2||A_3,salt=absent,info="ssjack-appstore/v1/master",L=32)`. Clear intermediates where possible; retain M only in owned unlocked memory context, clear on close where possible, refuse after close. One KDF process-wide; ~1GiB excluded from 32MiB non-KDF cap. Runtime copies/swap/dumps are not guaranteed erased. Application-store dedicated-master versus any shared-unlock alternative is a product decision; this proposal chooses a dedicated master. Sharing requires explicit product and independent crypto approval and is not implied.

`AES-256-GCM` uses exactly 12-byte nonces and 16-byte tags. For each chunk `i` and final record, initialize `B_0` to that record's exact plaintext. For data chunk `i`, layer `j`: `B_(j+1)=AES256GCM.Seal(K_(i,j),N_(i,j),B_j,AAD_(i,j))`, j=0..999. Output B_1000, length plaintext+16000; Open reverse j=999..0, require every tag; clear each intermediate buffer after use where possible.

- `ctx=ASCII("ssjack-appstore/v1/data/chunk/")||store_id[16]||snapshot_id[16]||u32be(i)||u32be(j)`; `K=HKDF-SHA-256(M,nil,ctx,32)`.
- `N=first12(HMAC-SHA-256(key=nonce_base[12],data=ASCII("ssjack-appstore/v1/nonce")||store_id||snapshot_id||u32be(i)||u32be(j)))`.
- AAD = `header[0:208] || nonce_base || u32be(i) || u32be(j) || u32be(plain_len) || u32be(cipher_len) || ASCII("SSAPP chunk layer")`.

Final index `0xffffffff`; context domain `ssjack-appstore/v1/data/final/`, nonce domain `ssjack-appstore/v1/nonce/final`; same identity/index/layer fields. AAD=`header[0:208]||nonce_base||u32be(final_index)||u32be(j)||u32be(48)||u32be(16048)||ASCII("SSAPP final layer")`. Same recurrence. Every chunk and final record has 1000 AES-GCM seals. No extra separators. Derive transient keys, clear where possible.

## Nonce uniqueness and anchor

Use the exact authenticated two-phase CAS protocol, canonical anchor state and chained fixed journal entries specified in [IO](IO.md); neither local journal nor rename is commit authority. Serialize per store. Anchor reservation CAS advances journal count/head before encryption; commit CAS changes committed tuple only after candidate and exact prior recovery ciphertext are durable and candidate is reread/verified. Maximum 2^20 reservations. Never remove/reuse a reservation, including after abort/cancel. Anchor prefix mismatch, journal loss/corruption, uncertain durability, exhaustion, or unavailable/ambiguous anchor blocks new encryption/commit; reconcile authenticated state, otherwise require explicit human recovery/new master/store. Collision consumes a reservation and uses a fresh pair before encryption. Local rollback of both data and journal cannot be detected without anchor. Authentication detects tampering/reordering/truncation/substitution, not valid-file rollback alone. Custom construction needs independent audit; 1000 layers do not give 1000-fold password resistance.
