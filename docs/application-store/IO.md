# Streaming, publication and recovery

## Streaming and release

Caps in [FORMAT](FORMAT.md): <=32MiB non-KDF memory/operation; one process-wide KDF (~1GiB excluded); <=2 active operations; one writer/store. Read one opened source handle into a private exclusive no-follow ciphertext-only spool, compute its encoded-file SHA-256, capture file identity/revision, and pin that handle. Authenticate final record, every chunk, catalog and exact length in pass one; emit no consumer bytes. Before pass two, recheck identity and full encoded-file hash against the captured hash, reauthorize the exact object/version/snapshot and fixed sink, then sequentially reread that same pinned spool. Hold the private spool's exclusive ownership/lock across both passes; the open handle and identity must remain pinned, and no other process or thread may mutate or replace its bytes. This is a protected immutable-spool assumption, not protection against hostile root or a compromised same-UID process. For each intersecting chunk, authenticate all 1000 layers into a bounded chunk buffer before emitting any bytes from that chunk; a tag failure stops before that chunk is delivered. Select only the requested object's authenticated byte range (catalog offsets are relative to concatenated payload after the catalog; a chunk can contain several objects), and stream verified selected bytes to the authorized sink with bounded backpressure. Clear each chunk buffer after use. Recheck file identity and full hash after pass two. A mismatch discovered then cannot stop bytes already streamed or retract them: report partial/unknown delivery and integrity failure. Do not reread a mutable path, stage plaintext to disk, or expose a generic secret-get API. If the spool cannot be pinned, locked and protected for both passes, refuse.

The 32MiB cap bounds buffers, not object size. Large objects are streamed chunkwise; no whole-object buffer is required. A sink can receive a prefix before a later spool, tag, revocation or sink failure. Report partial/unknown delivery after any handoff; no atomic sink delivery or adoption is implied, and a lost acknowledgement does not prove adoption. Reauthorize immediately before handoff and stop on observed revocation; bytes already consumed cannot be recalled. `SecretRef` is typed identity/version, not permission. Authorization binds consumer, deployment/target, code/config revision, object/version/snapshot, purpose, fixed sink, lifetime and revocation. Model sees references only; trusted #131 policy authorizes the consumer and #146 owns final sink verification/adoption. Never expose secrets to argv, environment, logs, tool output or model context, or send them through model-visible/untrusted pipes. Trusted, fixed, confidential final-sink IPC is permitted to carry authorized plaintext in memory; it must not durably stage plaintext, and the prohibition on untrusted pipes does not ban that approved IPC.

Unknown/non-repeatable sources are refused. A repeatable immutable source provides exact length and stable revision: sizing pass, stream pass, compare revision/length; mismatch discards candidate. No plaintext staging.

The trusted boundary is an enrolled, authorized per-store writer client using the human-enrolled writer credential and validating authenticated service replies; the service must enforce writer versus read-only roles and CAS the exact expected-state hash atomically. A CAS DTO carries expected state hash and proposed 192-byte new state, but no journal entry or full journal. Therefore the server can verify caller authorization, canonical DTO/state encoding, expected-state equality and serialized state replacement; it cannot independently establish that a new journal head extends the correct prior head, that snapshot/txn IDs are fresh, or that the committed tuple/candidate is valid. Those semantic checks remain the trusted writer's responsibility. The service's CAS is not proof of a valid application transition.

Acceptance cases (contract, not implementation evidence): expected-state CAS succeeds once; stale expected-state CAS conflicts without changing state; read-only/unauthorized client mutation is rejected; identical authorized replay is idempotent and returns the original outcome; an authorized malicious writer can submit a canonical but semantically invalid transition and is not prevented by this DTO/service contract; compromised anchor signing/service trust can forge state and defeats anchor guarantees; restoring old local snapshot/journal while the trusted anchor remains current is detected by tuple/prefix mismatch. No protection is claimed against a legitimate authorized writer acting maliciously or a compromised keeper holding the master. Rollback of both data and the trusted anchor, or anchor compromise, is outside the protection boundary.

## Authenticated anchor protocol (proposal)

Serialize transactions per store with an exclusive cooperative lock; reject lock contention. The external per-store anchor must provide durable, linearizable `Read`, `CreateIfAbsent`, and compare-and-swap (CAS), authenticated replies, and idempotency. Human enrollment provisions an out-of-band trusted Ed25519 service public key plus distinct per-store writer and read-only credentials; the writer may CreateIfAbsent/CAS/Read and the reader may Read only. Client-to-service authentication and confidentiality use a standardized authenticated secure transport, such as TLS 1.3 mutual TLS with human-enrolled client certificates; credential enrollment and trust binding are prerequisites, not a new cryptographic credential protocol or an endpoint implementation specified here. Disable TLS 1.3 early data (0-RTT) for every request; mutations are sent only after handshake completion, with application idempotency still required. The service enforces the enrolled per-store role on every operation, and the client authenticates service identity and authorizes each operation locally. The client validates the journal prefix and state transitions described here; the service's CAS and authentication establish serialized, authenticated state updates, not application-level journal validity. The proposal trusts an authorized writer to generate valid transitions. CAS/authentication alone do not enforce the journal rules or prevent a malicious authorized writer from regressing state. Do not assume the service can validate journal semantics without a DTO carrying the required journal data. Compromise of the writer credential or writer undermines rollback guarantees, since the malicious writer can submit authenticated mutations that violate the intended history. Model/MCP never receives credentials or arbitrary anchor access. Lost reply is unknown and reconciled by authenticated Read. Service/root compromise can forge history; this protocol is not a distributed transaction. Enrollment and deployment/trust of an actual service remain human decisions, not approved or existing guarantees.

Canonical request DTOs use big-endian integers, exact fixed lengths, zero reserved bytes, SHA-256 hashes, 16-byte IDs, and ASCII magic `SSASREQ1`[8]. Read is exactly 48 bytes (8+1+7+16+16): magic[8] || op=1:u8 || reserved[7]=0 || store_id[16] || request_id[16]. Each Read gets a fresh cryptographically random request_id. CreateIfAbsent is exactly 272 bytes (48+192+32): common 48 bytes with op=2 || state0[192] || idempotency_key[32], where key=`SHA256(ASCII("SSAPP-CREATE-v1")||store_id[16]||state0[192])`. CAS is exactly 304 bytes (48+32+192+32): common 48 bytes with op=3 || expected_state_hash[32] || new_state[192] || idempotency_key[32]. For every mutation, request_id is deterministic, never random, and uses a distinct operation domain: CreateIfAbsent=`first16(SHA256(ASCII("SSAPP-CREATE-REQUEST-ID-v1")||store_id[16]||idempotency_key[32]))`; Reserve=`first16(SHA256(ASCII("SSAPP-RESERVE-REQUEST-ID-v1")||store_id[16]||idempotency_key[32]))`; Commit=`first16(SHA256(ASCII("SSAPP-COMMIT-REQUEST-ID-v1")||store_id[16]||idempotency_key[32]))`. Mutation idempotency keys are immutable 32-byte values scoped to `(store_id, authenticated writer identity, logical operation)`; keys in this proposal are computed exactly as defined for CreateIfAbsent, Reserve and Commit. Same key and same canonical mutation must therefore recreate byte-identical request DTOs after restart. A mutation-key collision with a different canonical mutation is rejected and raises an operator-visible integrity error; do not generate a replacement key or request_id. The service namespaces request IDs and idempotency records by `(store_id, authenticated credential identity)`; it binds every reply to op, request_id, store_id and that credential, and rejects any request_id in that namespace already associated with different canonical request bytes. Durable idempotency records, including outcomes for rejected and conflicting mutations, must not be silently evicted; if capacity is exhausted, fail closed before accepting any new mutation. The reservation count does not bound all requests. A detected mutation request_id collision is terminal for that operation: fail closed, do not substitute a random/new ID, and require a new logical mutation only after authoritative reconciliation. A Read whose fresh random request_id collides with an outstanding/different request in that namespace is rejected; the client may issue a new Read with another fresh random ID. Read IDs are never used for mutations. Reject any wrong length, magic, op, reserved field, store, hash, key or noncanonical state before mutation.

Canonical reply is exactly 352 bytes (8+1+1+6+16+16+8+2+6+192+32+64): `SSASRSP1`[8] || op:u8 || outcome:u8 || reserved[6]=0 || request_id[16] || store_id[16] || service_version:u64 || state_len:u16 || reserved[6]=0 || state_slot[192] || state_hash[32] || signature[64]. Offsets: magic 0..8, op 8, outcome 9, reserved 10..16, request_id 16..32, store_id 32..48, service_version 48..56, state_len 56..58, reserved 58..64, state_slot 64..256, state_hash 256..288, signature 288..352. Ed25519 signs bytes 0..288 exactly, protecting op, outcome, store_id, request_id, version, state length/state and hash. Outcomes: Read=1 with state_len=192 and canonical state; CreateIfAbsent/CAS Committed=2 with resulting state; Conflict=3 with current state; Rejected=4 with state_len=0; Unknown=5 with state_len=0; Read NotFound=6 with state_len=0 and service_version=0. When state_len=0, state_slot and state_hash are all zero; otherwise unused state_slot bytes are zero and state_hash equals SHA256(`SSAPP-ANCHOR-STATE-v1`||state). Read returns either the current state or authenticated NotFound; NotFound is valid only before store creation. Conflict is authenticated current state, not commit. Unknown means no result assertion. The signed reply bytes must match op/request_id/store_id; accept them only in the authenticated transport session for the request. `service_version` starts at zero on creation and increments by one for each successful mutation; Read does not change it. Idempotent mutation replay returns the same recorded operation outcome, result state and original service_version, with the request's deterministic request_id in a newly signed correlation-correct reply if needed. It must not return a later current state as though it were the original operation result. No application-level nonce or challenge is defined. The chosen standardized secure transport supplies its own authenticated anti-replay behavior. Transport replay metadata may be bounded, but the service's per-store/per-writer/op idempotency records must remain durable for the store's lifetime so stale retries or uncertain mutations remain resolvable. A Read reconciliation determines actual current state after Unknown. For an unknown CreateIfAbsent, Read first: exact canonical genesis means the required initial state exists; NotFound permits retrying only the byte-identical CreateIfAbsent request with the same deterministic request_id/idempotency key if durable replay permits it, followed by Read; any other state stops creation and requires reconciliation. `CreateIfAbsent` succeeds only when it creates exact genesis; existing state is never reset.

All integers are big-endian; hashes SHA-256; IDs 16 bytes; all-zero hash/ID allowed only for specified genesis/null fields. Anchor state V1 is exactly 192 bytes:

`ASCII("SSAS")[4] || u16 version=1 || u16 reserved=0 || store_id[16] || u64 sequence || committed_snapshot_id[16] || committed_file_hash[32] || committed_txn_id[16] || journal_count:u64 || journal_head[32] || reserved[56 zero]`.

Genesis: sequence/count zero, committed IDs/hash/txn zero, `journal_head=H0`. Enrollment uses this state. A post-enrollment state with zero committed tuple but nonzero reservation count is valid: no snapshot is committed yet; it must retain sequence zero and a valid journal head. After first commit sequence is one; thereafter it equals number of commits. Validate the zero/nonzero tuple all-or-none. State hash is `SHA256("SSAPP-ANCHOR-STATE-v1" || state_bytes)`. Store ID is part of every operation; reject mismatch, noncanonical length/reserved bytes, rollback sequence, or invalid genesis.

Journal entry is exactly 40 bytes: `u64 index || snapshot_id[16] || txn_id[16]`. Index starts at zero; IDs are nonzero. Define `H0=SHA256(ASCII("SSAPP-JOURNAL-GENESIS-v1")||store_id[16])`; for zero-indexed entry `i`, `H_(i+1)=SHA256(ASCII("SSAPP-JOURNAL-ENTRY-v1")||store_id[16]||H_i[32]||entry_i[40])`. Thus anchor `journal_count=n` requires `journal_head=H_n`. Maximum count is 2^20. Journal is append-only; flush entry and directory/metadata before anchor reservation CAS. The anchor's count/head, not a local file length, establishes reserved prefix. Local journal may contain a suffix after crash. Verify anchored prefix and chain every suffix. For each suffix entry in order, read anchor: if already present at its exact index/head, treat it as burned; if not anchored and head/count still equal its preceding entry, CAS that exact entry as a reservation and burn it; if any mismatch/ambiguity, stop for human recovery. Quarantine all ciphertext associated with suffix entries permanently: never encrypt, re-encrypt, recommit or adopt it. Only after suffix reconciliation may a fresh pair be appended at current anchored count and reserved before encryption. Never truncate or infer reservation from local pointer.

### Two-phase transaction

1. Read/authenticate anchor; validate journal prefix. Under lock choose fresh random snapshot_id and txn_id absent from anchored history and local retained objects; append entry at anchor count and flush entry plus directory/metadata. Compute chain head and CAS count+1/head with committed tuple and sequence unchanged. Idempotency key=`SHA256(ASCII("SSAPP-RESERVE-v1")||store_id[16]||entry[40])`. Its deterministic request_id is computed by the mutation rule above. After any unknown CAS result (including timeout, lost reply or crash), perform authenticated Read first. If the current state is exactly the intended post-reservation state with this entry at the exact index/head, reservation is confirmed. If it is exactly the authenticated expected predecessor state, retry only the identical canonical CAS bytes with the same idempotency key/request_id, if the service's durable replay semantics permit; then Read again. Otherwise reconcile against the current authoritative tuple and stop; never encrypt using this reservation until its exact entry is confirmed. Snapshot/version ID collisions discovered after encryption burn the reservation and ciphertext; never re-encrypt or recommit. Fresh random version IDs are checked against all known retained/anchored pairs; historical collision-free allocation cannot be guaranteed without complete history.
2. If no committed snapshot exists (zero committed tuple), no prior ciphertext is due. Otherwise copy prior ciphertext exactly, verify expected revision, flush file and directory/metadata, reopen and verify hash. If required durability is unsupported, stop before encryption. Then write candidate exclusively/no-follow, bound to reserved snapshot_id and current committed parent, txn_id as transaction identity. Flush file and metadata, reopen and verify exact encoded hash and all tags/catalog/spans/length. After candidate and recovery copy durability, construct exact new 192-byte state (sequence+1, candidate snapshot/hash/txn, same journal count/head), expected reservation-state hash and key=`SHA256(ASCII("SSAPP-COMMIT-v1")||store_id[16]||txn_id[16]||candidate_file_hash[32])`. Append and fsync intent containing txn, expected hash, exact new state bytes, key and candidate hash; flush containing metadata. No CAS until intent is durable. Intent record is exactly 312 bytes (8+16+32+192+32+32): `ASCII("SSAPCMT1")[8] || txn_id[16] || expected_state_hash[32] || new_state[192] || idempotency_key[32] || candidate_file_hash[32]`. Create exclusive/no-follow in private transaction directory; reject duplicate filenames/ownership mismatch. Write exact bytes, fsync file and containing directory, reopen and byte-compare; validate magic, sizes, state encoding, txn, expected hash, key and candidate hash against candidate before sending CAS. Intent is immutable; never overwrite or synthesize on restart. After intent bytes and directory are durably verified, submit the canonical CAS once. On any `Conflict` or unknown result (including timeout, lost reply or crash), perform authenticated `Read` first. If current state exactly equals the intent's new state, commit is confirmed. If it exactly equals the intent's expected state, retry only the byte-identical canonical CAS with the same idempotency key/request_id if durable replay semantics permit, then Read again. Otherwise reconcile against the current authoritative tuple and do not send this CAS. Never claim commit before anchor confirms it.

If exact txn/hash is committed, update local pointer/cache to that tuple and fsync pointer and containing directory before releasing exclusive writer lock; if not durable, report pointer-lag and repair from anchor. Current readers authenticate anchor and require local current snapshot/hash/txn to equal committed tuple. On mismatch they release shared lock, close/discard pinned spool, then either return bounded retry or acquire exclusive recovery lock. Under exclusive lock reread/authenticate anchor, verify the exact anchored candidate and encoded hash, repair pointer and fsync pointer plus directory; never roll anchor back. Release exclusive lock, reacquire shared lock, reread anchor and pointer, require exact tuple match, then open and pin a fresh spool. No in-place lock upgrade and no waiting for exclusive repair while holding shared lock. Bound retries; otherwise fail closed. Historical SecretRef: do not compare to current anchor tuple; require independently trusted captured expected `(store_id,snapshot_id,encoded_file_hash)` plus authorization, then verify exact retained bytes/hash. Missing expectation or retained snapshot fails closed. Never select by filename or substitute current snapshot. On restart, an fsynced intent enables authenticated read and replay the exact CAS only if anchor still equals intent's expected state; if another state is present, reconcile by authenticated read without sending CAS. If anchor remains expected reservation state after restart and no intent exists, quarantine/burn candidate and reservation; reserve fresh IDs for any new encryption. Never construct a new CAS for an old candidate. Any other advanced state requires lineage reconciliation. Live and restarted operations follow the same read-first rule after an unknown result: retry only byte-identical CAS bytes with the same idempotency key/request_id if authenticated Read still shows the exact expected state and durable service replay permits it. Ambiguity/offline is pending; never reparent or re-encrypt. Location/identity binding: txn_id is not a snapshot wire field. Maintain a private immutable sidecar mapping `(store_id,snapshot_id,encoded_file_hash)` to txn_id and exact candidate location; accept sidecar only if txn_id exists in anchored journal and file hash/tags verify. Locator is not authority; filenames alone prove nothing. Current anchor tuple includes txn_id.

Crash before reservation CAS: local suffix remains untrusted until chain-checked and CAS-reserved. Crash after reservation CAS/before encryption: consumed ID, no candidate. Crash during/after candidate write but before durable commit-intent record: prior commit authoritative; candidate is orphan and permanently quarantined. Crash after durable intent but before/during CAS: reconcile by authenticated read; replay the exact CAS only if anchor still equals intent's expected state; never generate a new request. Before commit CAS, prior committed state remains authoritative. After successful CAS, anchor's new tuple is authoritative even if local pointer lags; readers use the recovery procedure above. Never infer success from files or CAS timeout. Anchor unavailable, corruption, unknown reply or unsupported durability fails closed. No global transaction; recovery needs authenticated service and retained ciphertext.

## Release, rollback and lifecycle

Current reads use anchor-bound committed tuple. Historical refs use captured expected tuple, never current anchor equality. Before bytes reach the sink, pass one authenticates the entire exact snapshot, transcript, catalog, all chunk tags and exact object span and records the full encoded hash. Pass two verifies the same pinned, exclusively locked spool identity and hash before first byte, reauthenticates each needed chunk and its selected range before streaming, then verifies identity and full hash again at completion. Each chunk's selected plaintext is emitted only after all its 1000 tags pass; a tag failure stops before that chunk, though an earlier prefix may have reached the sink. A full-file hash or identity mismatch discovered only after pass two does not revoke already streamed output; report integrity failure and partial/unknown delivery. Reauthorize exact object/version/snapshot, consumer, scope and sink immediately before handoff. Stop on observed revocation; bytes already delivered cannot be recalled. Clear passphrase, derived temporaries and chunk buffers after use where possible. Report partial/unknown after any possible handoff; a sink failure cannot guarantee no delivery. Keep desired/delivered/adopted distinct. #131 owns consumer authorization; #146 owns trusted final-sink verification/adoption. Neither is solved by storage commit; no assumed live reload, restart or fallback. Watchers are wake-only.

Without external anchor, rollback of valid old bytes is undetectable. Anchor mismatch blocks normal updates. Human-authorized recovery validates backup and publishes a new child with fresh ID through the same reservation/commit protocol; never silently install old bytes as current. Lost master is unrecoverable; credential revocation is independent. GC only after anchor/recovery references are readable; retain exact encrypted copies and never delete early.

Per-store lock spans read/reconcile/reserve/encrypt/commit/pointer update. Process caps and cancellation apply; cancellation after reservation consumes it. No local atomic rename, file durability, or service behavior is claimed without platform/service evidence. Hash-chain history provides integrity only with the trusted anchor key; it does not resist compromise of the external service/key.
