## 1. Placement

**Recommendation: add a distinct binding kind/profile, not an auth mode on an existing remote-MCP account.** Existing account auth represents HTTP credentials (`none`, `bearer`, `basic`, custom headers); a signed mcp-jack identity also has a signer, audience, independent server trust pin and rotation state. Combining the two would blur credential meaning and permit accidental fallback. Existing normal bindings remain unchanged. [ssjack code] `docs/REMOTE-MCP.md:21-41`; `internal/mcpdirectory/types.go:17-49`.

The signed client belongs in the startup-process keeper/runtime, between the existing bridge's inventory/call boundary and its HTTP exchange. The bridge can keep its existing namespace, frozen inventory and describe/call-only channel. A mcp-jack adapter should implement the existing upstream-handle shape while retaining the client and signer privately; no signing API or auth data is added to the child wire. [ssjack code] `docs/REMOTE-MCP-RUNTIME.md:11-20,22-30`; `internal/mcpbridge/facade.go:1-4,14-19,53-56`; `internal/mcpbridge/internal/supervisor/bounds.go:22-45`.

```text
Harness/model
  | namespaced tool + arguments only
  v
ssjack child bridge -- existing binding namespace and describe/call channel
  | binding ordinal/tool only; no URL, signer, pin, invite, or signature input
  v
keeper process -- mcp-jack client + vault-backed signer/trust state
  | POST with per-request Jack-Auth; verify response before returning data
  v
mcp-jack gateway -- verifies identity/replay; dispatches to MCP application
```

The server gateway is a separately operated Linux service; the client-side integration must remain cross-platform. [mcp-jack code] `README.md:53`; [assumption] client-side support is proposed for Windows, macOS and Linux.

**Rejected:** making the harness invoke `jack` or supply an auth header; using its existing HTTP bearer-header account; direct access to mcp-jack admin/auth tools. These expose protocol inputs or turn signing into model-controlled authority, contrary to the current private-handle runtime boundary. [ssjack code] `docs/REMOTE-MCP-RUNTIME.md:3-9,11-20`; [mcp-jack code] `spec/03-user-management.md:5-14`.

## 2. Credentials and enrollment

Add an optional backward-compatible field to the existing encrypted remote-MCP directory records for mcp-jack configuration. Preserve current records and default behavior when absent; use strict validation and exact revision-bound owner mutations. Store the Ed25519 user seed encrypted in the vault, plus public `kid`; store the independently provisioned pinned server public key and `kid`, `aud`, fixed endpoint, and profile/era selection with the binding. [assumption] Versioned record encoding and migration/older-reader behavior must be designed before implementation; existing directory records live in the encrypted payload and the vault currently has a `remote_mcp` field. [ssjack code] `internal/vault/internal/core/vault.go:31-45,110-119`; `internal/mcpdirectory/types.go:17-49`; `docs/REMOTE-MCP.md:21-45`.

Do not place seed, pin, invite code, signature material or auth configuration in argv, environment, logs, harness config, or worktree files. Keep secrets in vault-owned buffers, pass only a private signer interface to the client, clear owned buffers on close, and scrub any temporary enrollment input. Existing owner forms mark secret input as hidden and remote-MCP credentials are captured privately. [ssjack code] `internal/ownermcp/forms.go:49-73`; `internal/mcpdirectory/types.go:55-82`; `docs/REMOTE-MCP.md:198-203`; [mcp-jack code] `client/transport.go:391-406`.

**Owner enrollment flow (proposed):** owner chooses “Enroll mcp-jack” in the existing owner menu or equivalent `owner` command; chooses the configured signed binding, enters invite code in an interactive hidden field and confirms the user name/admin expectation and endpoint/audience/server-key fingerprint; ssjack generates the new Ed25519 key locally, calls `Enroll(code,name,newSigner)` through the signed client, and only on a verified success persists seed and public identity by revision-checked vault save. No invite input is ever an option argument. The exact owner menu/command and human confirmation are owner decisions. [assumption] The existing owner command/TUI use shared typed private forms; `ownermcp.Fields` currently has only remote-MCP endpoint/account actions. [ssjack code] `docs/REMOTE-MCP.md:49-67`; `internal/ownermcp/forms.go:31-73`; [mcp-jack code] `client/tools.go:163-178`; `spec/03-user-management.md:47-68`.

Only a human owner with an unlocked, healthy vault may initiate enrollment, key replacement, server pin provisioning/refresh, or revocation management. An agent can call only inventory-listed ordinary upstream tools; it never obtains the seed, pinned key, invite, server admin tool, signature header or signing input. [assumption] [ssjack code] `docs/REMOTE-MCP-RUNTIME.md:11-20,67-80`; `docs/REMOTE-MCP.md:63-67`.

User-key rotation must be an explicit owner action: generate replacement key, invoke `RotateKey` with old-key request and new-key proof, then persist new seed only after verified success. If outcome is uncertain, do not retry automatically; reconcile owner-side status/revocation out of band. Revoke a compromised/retired identity through server administration, then explicitly remove or disable its local binding. Signed authenticated rejection is reported as a fixed failure; unsigned 401 supplies status only, never an actionable body. [mcp-jack code] `client/tools.go:190-213`; `spec/03-user-management.md:35-45`; `client/transport.go:68-78`; [ssjack code] `internal/mcpbridge/internal/supervisor/bounds.go:49-56,41-45`.

Add seed, invite, pinned-key and any derived signing literals to known-output masking before first bridge access. Mask output content and inventory prose; refuse rather than rewrite schema strings/keys when masking changes semantics. Keep fixed diagnostics and mandatory keeper/channel-token masking even if the trusted-terminal known-literal filter is disabled. [ssjack code] `docs/REMOTE-MCP-RUNTIME.md:67-80`; `docs/REMOTE-MCP.md:265-286,298-310`; `internal/mcphttp/auth.go:93-120`.

## 3. Server-key rotation

The upstream `ClientTrustState` interface is merged and available; ssjack's vault-backed adapter implementing whole-snapshot CAS remains open. Its contract compares the full expected snapshot and captured ClockGuard tuple, writes the complete desired snapshot with exactly one trust-revision increment, and fails closed; a per-binding writer token serializes refreshes. [mcp-jack code] `client/rotation/trust_state.go:5-54`; `spec/candidate/server-key-rotation.md:104-110`; [assumption] keeper ownership and vault adapter implementation. The captured clock tuple is not time authority and is only compared; the trust compare-and-swap must never modify the clock guard (a newer high-water mark or an unsafe latch must not be overwritten), and a clock advance that happened before the swap is a definite conflict, not a retry [mcp-jack code: `spec/candidate/server-key-rotation.md:106,110,114-116`].

Publication occurs at time P, with activation A=P+172800 s=P+48 h; the predecessor remains valid until the successor activates and is cut off strictly at activation. [mcp-jack code] `README.md:131-134`.

| Failure/recovery state | Required behavior |
|---|---|
| Unknown or dirty trust state | Fail closed; explicit owner repair. [mcp-jack code] `README.md:139-144`; `client/rotation/controller.go:49-60,71-79`. |
| Failure before compare-and-swap (network, timeout, verification) | Trust chain unchanged, but `CheckSnapshotClock` may already have advanced or latched the durable clock guard before CAS; owner retry is allowed only after a fresh state check reports healthy and unfenced. [mcp-jack code] `client/rotation/refresh.go:151-165`; `durable/internal/rotationstore/trust.go:183-215`. |
| Compare-and-swap reports unknown outcome | State unknown; fail closed; persist a binding-wide fence that survives restart. Reconcile only against the exact expected or exact desired snapshot/revision; never adopt tentative state or repeat callback. [mcp-jack code] `spec/candidate/server-key-rotation.md:108-112`; [assumption] vault adapter durably enforces the fence. |
| Swap committed, but final gate failed | Stored state has changed; owner message must say so, and next call starts from a re-read snapshot. [mcp-jack code] `client/rotation/refresh.go:151-169`. |
| Clock regression/unsafe latch or invalid interval/capacity | Fail closed until owner repair; retain high-water, `timeValid` interval/window and `capacityValid` gates. [mcp-jack code] `client/rotation/controller.go:130-165`; `README.md:139-144`. |
| Clock rollback latch (`rotation_clock_unsafe`) | Fail closed until owner repair; never auto-clear the unsafe latch. [mcp-jack code] `durable/internal/rotationstore/trust.go:195-215`; `spec/candidate/server-key-rotation.md:112-114`. |


For ordinary calls, plain `client.Transport` verifies against one fixed pinned `ServerKey`; rotation-enabled bindings instead run controller-style verification from the keeper's vault trust snapshot: accepted `kid` → key entries with `NotBefore`/`KnownCutoff`, a per-call outer gate (known kid, 1 MiB body cap, raw clock), then the final `CheckSnapshotClock` high-water, `timeValid` and `capacityValid` gate. Cutover publishes one next key at publication time P; the successor activates at A=P+48 h; both keys verify during overlap, with a strict predecessor cutoff at activation. [mcp-jack code] `client/transport.go:108-130,260-267`; `client/rotation/controller.go:99-127,130-165`; `README.md:131-134`. [assumption] The vault adapter and ordinary-call integration are new; adapter entry-point compatibility must be confirmed with the mcp-jack repository.

Refresh is a named explicit owner action fetching exactly one bounded page; it must show verified outcome and whether a snapshot committed. [mcp-jack code] `client/rotation/refresh.go:91-103`; `README.md:131-134`; [assumption] owner surface.

## 4. Transport and tunnel

Use `mcp-jack/client` as the signing/verifying transport. Its RoundTripper signs each request and verifies the response before body delivery; response cap is 1 MiB. It requires HTTPS for any host, allows HTTP only for canonical literal loopback, refuses 301/302/303/307/308 without following, and does not resolve names. Signatures do not encrypt; TLS is required off loopback. A 401 without verified response authentication is status-only. [mcp-jack code] `client/transport.go:108-123,145-163`; `client/internal/urlpolicy/urlpolicy.go:16-25,37-81`; `client/transport.go:234-240`; `client/transport.go:68-78`; `spec/01-authentication.md:9-12,93-129`.

For a gateway reachable only on the SSH side, propose an `http.RoundTripper` base that carries the request through ssjack's existing selected SSH route and connects only to the designated loopback gateway. Keep the upstream URL literal loopback `http://127.0.0.1:port/...` so the mcp-jack URL policy accepts it; the private adapter must map that request to a host-verified SSH tunnel, not a local machine listener or direct network fallback. Existing SSH proxy configuration supports direct/SOCKS5/HTTP CONNECT and does not itself tunnel HTTP through the selected SSH server; this gateway-over-SSH adapter would be new. [ssjack code] `docs/PROXY.md:8-19,42-59`; `internal/sshproxy/dial.go:10-32`; [mcp-jack code] `client/internal/urlpolicy/urlpolicy.go:20-25,69-81`; [assumption] proposed SSH-bound RoundTripper.

**Upstream transport seam (merged):** `client/rotation.NewHTTPWithTransport(store ClientTrustState, signer client.Signer, timeout time.Duration, base http.RoundTripper)` accepts a caller transport, and every attempt uses it. The seam is available; the remaining SSH-bound transport/tunnel implementation is ssjack work. Keep the upstream URL literal loopback and route only through the selected verified SSH tunnel; never direct-dial or fail open. Until the ssjack route exists, refuse rotation refresh with a clear owner-visible message. [mcp-jack code] `client/rotation/http.go:37-68,115-131`; [assumption] ssjack SSH-bound implementation and refusal behavior.

**Endpoint-policy conflict:** current ssjack `mcphttp` accepts only HTTPS endpoints and rejects non-public literal/resolved addresses, while mcp-jack explicitly allows literal-loopback HTTP for local gateway deployments. Reusing `mcphttp.NewUpstream` unchanged would reject the loopback gateway. Do not weaken generic endpoint validation: implement a distinct, narrow signed-gateway route policy with fixed loopback URL and SSH-tunnel dial only, or use an HTTPS gateway URL and a validated TLS route if that is proven compatible. [ssjack code] `internal/mcphttp/policy.go:23-47,74-109`; [mcp-jack code] `client/internal/urlpolicy/urlpolicy.go:20-25`; [assumption] solution choice.

Bound request/response sizes, header bytes, connection count, concurrency, call deadlines and total lifetime; reject redirects and never transparently retry uncertain side effects. Existing ssjack exchange has 64 KiB request, 256 KiB response, 16 KiB headers, four active operations, 4096 messages, 10-minute lease and 20-second operation budget. The mcp-jack transport independently permits 1 MiB response; adapter should apply the tighter remote-bridge result bounds and ensure the client cannot bypass cancellation. [ssjack code] `internal/mcpflow/transport.go:16-30,59-67`; `internal/mcpbridge/internal/supervisor/bounds.go:30-45`; [mcp-jack code] `client/transport.go:152-153`.

**Signed exchange layering**

[assumption] Choose one layering: a narrow signed adapter RoundTripper below `mcpflow`. Today callers cannot supply `Jack-Auth`: request admission defaults to rejection for it. Only the adapter produces `Jack-Auth`, appending it to the prepared request after admission; thus the harness, MCP SDK and upstream request builder cannot supply or influence it. [ssjack code] `internal/mcpflow/transport.go:128-155`; [assumption] adapter placement and signing-header ownership.

On response, the adapter consumes and strips `Jack-Auth` immediately after its base `RoundTrip` returns, before `mcpflow.responseHeaders()`; the existing three-header allowlist stays unchanged. A verified signed non-2xx rejection becomes a private, `errors.Is`-checkable category consumed only inside the adapter/mcpflow boundary. mcpflow returns definite refusal with the same fixed public text; mcpexchange maps `DefiniteResponse(err)` to `errExchange`, and the supervisor maps call errors to `errCallFailed`. The harness sees no signed-rejection-specific text. An unverified answer, including 401, is status-only with no trusted body. [ssjack code] `internal/mcpflow/transport.go:278-307`; `internal/mcpexchange/connection.go:251-255`; `internal/mcpbridge/internal/supervisor/session.go:266-269`; `internal/mcpbridge/internal/supervisor/bounds.go:49-56`; [mcp-jack code] `client/transport.go:250-267`; [assumption] private sentinel and adapter integration.

For this binding kind only, mcpflow admission continues to reject caller-supplied `Jack-Auth`; the adapter adds it only after admission. The response header is consumed before the unchanged response allowlist. Generic endpoint policy and `mcpexchange.New` remain unchanged: a signed-kind-only private constructor must bake the fixed loopback-over-SSH target into the capability, with no caller URL. [ssjack code] `internal/mcpflow/transport.go:128-155,234-251`; `internal/mcphttp/policy.go:23-47,74-89`; `internal/mcpexchange/exchange.go:80-94`. [assumption] Private constructor and capability scope.

Enforce the tighter 256 KiB ssjack response cap before mcp-jack's verifier buffers up to 1 MiB, using a limiting reader before the verifier or a bounded adapter read loop; mcpflow's later response-body cap cannot constrain that earlier buffering. A cap hit is unverified and maps to the fixed unreadable-response error. [ssjack code] `internal/mcpflow/transport.go:287-307,317-321`; [mcp-jack code] `client/transport.go:250-256`; [assumption] Pre-verification cap placement and error mapping.

## 5. What the harness sees

Expose only verified `tools/list` inventory and ordinary `tools/call` results, under existing per-binding digest namespace and existing frozen-inventory rules. The model cannot select endpoint, account, HTTP headers, request method, binding ordinal, auth mode or protocol-native tools. [ssjack code] `docs/REMOTE-MCP-RUNTIME.md:11-20,62-65`; `internal/mcpbridge/internal/supervisor/bounds.go:22-45,110-114`.

Signed rejections are indistinguishable from other definite refusals at the model surface: no signed-rejection-specific text or server-supplied body is exposed. Unsigned/unverified responses, redirect refusal, timeout, unknown server key, dirty/unknown rotation state and malformed transport also fail closed with fixed error text and no body. Do not retry. [assumption] [ssjack code] `internal/mcpexchange/connection.go:251-255`; `internal/mcpbridge/internal/supervisor/session.go:266-269`; `internal/mcpbridge/internal/supervisor/bounds.go:49-56`; `internal/mcpexchange/exchange.go:71`; `docs/REMOTE-MCP-RUNTIME.md:80-83`; [mcp-jack code] `client/transport.go:25-31,68-78`.

Never expose `jack.admin.*` to the model; default exposure of all `jack.*` protocol-native tools should be deny, including `jack.enroll`, `jack.whoami`, `jack.key.rotate`, and `jack.server.key`. The mcp-jack server uses admin flag only to gate reserved admin tools; ssjack's client facade must keep those out of model inventory even if a gateway lists them. [mcp-jack code] `spec/03-user-management.md:5-14,28-45,70-83`; [assumption] filtering policy.

Verified identity `{kid,name,admin}` may support owner-facing verified identity display and audit correlation only; it must not grant additional tools, infer human identity, or promote harness authorization. Ordinary MCP authorization remains the upstream application’s responsibility. Audit locally only sanitized binding ID, verified identity where appropriate, tool name, outcome category and duration; never seed, invite, signatures, raw arguments or bodies. Upstream protocol-native actions are audited by the server where they reach a tool, but server audit is best effort. [mcp-jack code] `README.md:26`; `spec/03-user-management.md:140-146`; `docs/threat-model.md:38-39`; [assumption] ssjack audit scope.
