# Application discovery and owner approval

**Status:** owner approvals and the interactive review flow are implemented. The bounded startup-discovery and route-ownership material below retains design and acceptance notes where not stated as implemented. Discovery improves convenience, never turns a worktree file into authorization.

## Current contract and constraints

Full mode registers applications supplied through repeatable `--app DIR` and admits owner-approved discovered applications at startup. `--app-route` is accepted only together with at least one explicit `--app` (`cmd/ssjack/internal/cli/fullmode.go:285-292`); after admission it acts as the lowest-priority fallback route, also covering discovered owner-approved applications without a higher-priority route: per-invocation `--app-route-for`, then the approval record's own route, then the global fallback (`cmd/ssjack/internal/routes/routes.go:59-81`; `cmd/ssjack/internal/cli/fullmode.go:142-154`). The working directory is scanned for discovered candidates, but PATH is not searched for applications (`docs/APP-CONTRACT.md:15-24`). Descriptors bind name, launch executable/arguments, workdir and command classes, but no route or selected profile/container/user (`docs/APP-CONTRACT.md:26-54`).

The current CLI defines `--app`, `--app-route`, and `--app-route-for` for applications (`cmd/ssjack/internal/cli/run.go:103-106`). Explicit `--app` descriptors and `--app-route` are validated before credentials load/unlock (`cmd/ssjack/internal/cli/fullmode.go:285-304`), while owner-approved discovered applications are admitted after vault unlock by comparing the startup scan against stored approvals (`cmd/ssjack/internal/cli/fullmode.go:81-126`). The working root is derived from `.` (`cmd/ssjack/internal/cli/run.go:290-293`). Descriptor parsing is bounded to 16 KiB, strict, rejects symlink/reparse-point directories and descriptor files, and confines workdir; executable resolution can use PATH for a bare executable (`internal/application/descriptor.go:18-28,55-137,234-304,319-386`). Existing cap is 16 and duplicate names are rejected (`internal/application/application.go:56-57`; `cmd/ssjack/internal/cli/fullmode.go:294-312`).

An admitted application is trusted code, launched directly with the keeper user's authority; it is not sandboxed (`internal/application/application.go:178-205`; `docs/APP-CONTRACT.md:66-68,109-113`). Route syntax currently uses container `^[a-z0-9][a-z0-9-]{0,62}$` and user `^[a-z_][a-z0-9_.-]{0,31}$` (`internal/application/application.go:22-25,77-100`; `docs/APP-CONTRACT.md:89-92`). Preserve these limits.

## Recommendation

### 1. Scan bounded candidates, do not enable them

When discovery runs, scan the current working root itself and its **immediate child directories only** (depth 1). Root may itself contain `ssjack-app.json`, allowing the working folder to be an app; each immediate child may be another candidate. Do not recurse. Examine at most 256 directory entries at depth 1; the root descriptor check is separate and fixed (one descriptor check, not a directory entry). Enforce a scan bound of 16 valid candidates total across root and children. If either the entry-count limit or valid-candidate limit is exceeded, report overflow and refuse discovery activation: no discovered approved app from that scan activates. Do not truncate, select an arbitrary subset, or activate a partial scan. These scan bounds are separate from the enabled runtime registration bound described below.

Enumerate entries without following links. Reject candidate directories, roots, or descriptor files that are symlinks, Windows junctions, or other reparse points; never traverse through them. Use the existing no-link and bounded-read discipline (`internal/application/descriptor.go:66-80,107-137`) and add platform-specific checks where needed. Canonicalize candidate directory identity, deduplicate canonical directories, and sort by normalized relative path (root first, then lexical normalized paths) before reporting. Candidate name conflicts are status-only during discovery; apply activation collision checks only to the enabled set described below.

Ignore these basenames at any child-directory position, case-insensitively as appropriate to the platform: `.git`, `.hg`, `.svn`, `node_modules`, `vendor`, `target`, `dist`, `build`, `.cache`, `.next`, `.venv`, `venv`, `__pycache__`. These are known metadata/dependency/generated/cache trees whose traversal is noisy and commonly contains copied descriptors; depth-1-only scanning already bounds exposure, and this explicit list avoids broad rules such as ignoring every hidden folder or arbitrary user-named directory. Do not ignore a directory for any other reason except inaccessible/unsafe entry or no descriptor; report why, subject to the diagnostic bound: report at most 16 rejection diagnostics, then one summary diagnostic for any further rejections. These are **candidates**, not enabled applications.

Scan and report candidates on startup by default, with no authorization or activation implied. Discovery is additive candidate status only: users with no approved discovered apps retain the exact current registration and `app_list` behavior. A discovered descriptor never silently registers an app merely because it exists. If startup is noninteractive, candidates remain pending and disabled until owner approval. Do not add `--discover`: because scanning/reporting is the default, the flag would be redundant; a presentation/refresh control could be considered separately if a concrete need emerges, but it must never be an authorization boundary. Existing `--app DIR` remains an explicit registration path, subject to current descriptor validation; decide separately whether future approvals are required for it rather than implicitly changing its contract in this additive feature.

### 2. Owner trust and approval record

Use candidate discovery only to identify bounded descriptor bytes and validate them; no candidate may be listed through MCP, routed, or executed until an owner approves it. Never execute to inspect. Approval is a distinct owner action after vault unlock and review. Approval records are persisted in the encrypted vault as owner-side data, not in the worktree descriptor or a world-readable project config. The approval record stores the application name, canonical directory path, descriptor fingerprint, and optional owner route; the keeper rechecks the descriptor fingerprint at approval time. The record does not store a native folder identity.

An approval record binds (1) the canonical JSON descriptor fingerprint, (2) the canonical directory path, and (3) an optional owner route. It does not persist native filesystem identity, so do not describe the record as binding a stable folder identity. Store only bounded validated metadata needed for owner presentation and subsequent matching. The approvals menu fingerprints its bounded scanned candidate; on an approve write the keeper independently re-derives the descriptor fingerprint from the canonical path and refuses a mismatch or invalid path. At startup, discovery compares the scanned candidate's canonical path and fingerprint with the stored approval; changed, missing, or invalid candidates are not enabled by that approval and require explicit review/reapproval. Revoke removes the approval; removal of a candidate cannot grant it.

A hostile project can plant descriptors, but they remain candidates only: no `app_list`, route, or launch until owner approval. Descriptor fingerprinting does not attest executable bytes, dependencies, PATH results, workdir contents or later file changes. Executable/workdir and their mutable contents remain trusted-code boundary; a descriptor can point at external executable paths and current bare-name resolution uses PATH (`internal/application/descriptor.go:319-363`). Descriptor-byte binding does not attest or freeze executable/workdir contents: they remain mutable/trusted code after admission. Do not claim approval prevents same-user or agent edits after startup. Discovery admission compares the scanned candidate with the approval and parses its bounded buffer; the separate keeper-side approval write re-derives the fingerprint from the canonical path. Application route is owner-controlled and never descriptor-controlled.

Alternative comparison: (a) candidates plus one-time owner approval bound to descriptor fingerprint and canonical path, encrypted in vault, is implemented; changed descriptors require review/reapproval. (b) A manually maintained owner config stored in the vault is also safe but less convenient for projects that appear/disappear; it can be the underlying record format. (c) A flag alone is insufficient protection and is not recommended as sole authorization: an agent or launcher can supply it, and it cannot express considered owner consent. `--discover` must not authorize activation; this proposal omits it because candidate scanning/reporting is the default.

### 3. Per-application route ownership

Keep `--app-route incus:CONTAINER:USER` **exactly unchanged** as a global route default. It still requires at least one explicit `--app` (`cmd/ssjack/internal/cli/fullmode.go:285-292`); discovered approvals alone do not satisfy that prerequisite. Route resolution is, highest to lowest: per-invocation `--app-route-for` override, the approval record's stored route (only for approved discovered applications, `cmd/ssjack/internal/routes/routes.go:74-81`), global `--app-route` fallback, then no route (`cmd/ssjack/internal/routes/routes.go:59-71`). The global fallback also supplies a route to discovered approved apps without a higher-priority binding (`cmd/ssjack/internal/cli/fullmode.go:142-154`). Add a distinct repeatable flag, `--app-route-for APP=incus:CONTAINER:USER`, to avoid overloading the old flag's grammar or ambiguous parsing. `APP` is the validated descriptor application name; parse the right-hand route with the existing route parser/regexes. Reject malformed values, unknown app names, duplicate bindings for an app (even identical repeats), and duplicate/colliding descriptor names. Repeated `--app-route-for` flags are valid when each names a different app. A route can be unset only by removing its persisted owner per-app binding; there is no empty or explicit no-route CLI override, so the global fallback applies when no per-app binding or invocation override exists.

Persist owner routes in the same encrypted vault application-owner configuration, never in `ssjack-app.json`. Route precedence is, highest to lowest: per-invocation `--app-route-for` override, the approval record's stored route (only for approved discovered applications), global `--app-route` fallback, then no route (`cmd/ssjack/internal/routes/routes.go:59-81`). The CLI override is supplied by the owner for that invocation only; it does not persist or rewrite vault settings. The legacy global flag remains compatible and supplies a route to applications without a higher-priority binding; do not copy it into individual persistent bindings during migration. The descriptor cannot choose profile, container, user, route, or override an owner setting.

### 4. Compatibility and root behavior

Keep `--app DIR` and the existing global `--app-route` working unchanged. No deprecations and no breaking descriptor-format change. Existing users with the old route retain a global default; do not auto-migrate it into per-app routes. Profiles continue to be selected by the normal CLI/vault path, never by a descriptor. Discovery of root plus direct children supports the root as one application and multiple immediate nested applications at once, with at most 256 depth-1 directory entries examined and at most 16 valid candidates; no recursive search. Explicit repeatable `--app` remains usable alongside discovery, with canonical directory deduplication. The enabled-set name-collision check includes only approved discovered apps and explicit `--app` registrations: unapproved/rejected candidates are status-only and cannot collide with or block explicit registration. If approved discovered apps collide with explicit registration names or with each other, fail closed for activation of the collision; never choose by order. The total enabled runtime registrations across discovered-approved apps and explicit `--app` entries must never exceed the existing `MaxApplications` limit of 16 (deduplicate the same canonical directory). If that total would exceed 16, refuse/report the overflow; do not truncate or select entries by order.

### 5. Startup and owner UX

Preserve the existing pre-unlock safety property: explicit descriptors are validated before credentials are loaded (`cmd/ssjack/internal/cli/fullmode.go:285-304`). Discovery may enumerate and read only bounded descriptor bytes before unlock, validate candidates, and report safe candidate/rejection metadata. It must not execute candidate code or activate/list candidates before unlock. After vault unlock, compare stored approvals with the scan by canonical path and fingerprint; for a match, re-check the scanned directory identity before parsing the captured buffer for registration (`cmd/ssjack/internal/cli/fullmode.go:108-120`; `cmd/ssjack/internal/discover/integrate.go:37-59`). The fingerprint is SHA-256 over canonical JSON, so whitespace- or line-ending-only descriptor edits do not change it; a canonical-JSON change marks the record changed and requires reapproval (`internal/application/discovery/fingerprint.go:9-18`; `cmd/ssjack/internal/discover/integrate.go:45-47`). New, changed, or rejected candidates remain disabled pending an explicit owner action. An invalid candidate should not be silently dropped from a review; present its safe reason, but do not make discovery of an invalid unrelated entry execute or authorize anything. On scan overflow, report overflow and activate no discovered approved apps from that scan. A scanned folder without `ssjack-app.json` is not a candidate and is neither reported nor shown as a rejection; only real rejections (unreadable, unsafe or invalid descriptors, unsafe entries) are.

Owner-facing status should distinguish **candidate**, **approved/enabled**, **rejected/ignored**, **changed—approval required**, and **unsafe/invalid**. Show validated name (if safe), normalized relative path and truncated descriptor hash; give concise reason codes/messages. Escape/quote terminal metadata and never print raw uncontrolled descriptor text, raw JSON, or terminal controls. Do not echo launch args or other uncontrolled values. Existing owner UI principles mask secrets, quote terminal controls and avoid raw backend errors (`docs/application-store/OWNER-TUI.md:19-31`). Proposed startup/status wording (illustrative; substitute values only after validation, and terminal-escape/quote every displayed value):

```text
Application candidate 'foo' at ./services/foo (not approved; review in --interactive)
Application 'foo' changed since approval; disabled until owner re-approves
Application candidate at ./services/foo is invalid (descriptor_name_invalid; disabled)
Application 'foo' approved and enabled at ./services/foo
Application 'foo' rejected/ignored; disabled
```

If a name or path cannot be validated and safely escaped, omit it and show only a fixed status/reason code; never interpolate raw descriptor content or controls. Startup scan/report may happen by default but never activates a candidate. Approval requires an explicit owner action. Existing valid `--app DIR` registration and `--app-route incus:CONTAINER:USER` global-default semantics remain unchanged. Per-app invocation override is owner-supplied `--app-route-for APP=incus:CONTAINER:USER`, applies for that invocation only, and never comes from the descriptor.

Exact concise proposed help entries:

```text
--app-route-for APP=incus:CONTAINER:USER
                                    Owner-supplied per-app route override for this invocation only (repeat for different apps).
Application discovery (default): checks the working folder and immediate subfolders for candidate descriptors; candidates require owner approval and are never enabled automatically.
--app DIR
                                    Explicitly register an application from DIR.
```

Keep the existing entries and meanings for `--app DIR` and `--app-route incus:CONTAINER:USER`; the current help lists `--app DIR`, `--app-route incus:C:U`, and `--app-route-for APP=incus:C:U` (an owner-supplied per-app route override for this invocation only), plus the discovery note: “Application discovery (default): checks the working folder and immediate subfolders for candidate descriptors; candidates require owner approval and are never enabled automatically.” (`cmd/ssjack/internal/help/help.go:101-102`). Do not add `--discover`; default scanning makes it redundant, and no CLI flag grants approval.

The interactive owner menu now includes **Application approvals**. It scans the working folder and its immediate children and shows candidates as candidate, approved, changed, rejected, or unsafe, with safe name/path, shortened current and approved hashes, and a reason where available. An approval record whose folder is absent from the scan is also shown as changed with a reason such as `descriptor_missing`, `outside_workdir`, or `not_scanned`. Overflow is shown as unsafe rather than displaying a partial candidate list. Use Up/Down to select; `a` arms approve, `r` arms reject/ignore, and `x` arms revoke; Enter/`y` confirms and Esc/`n` cancels. Approve is available for a candidate or changed descriptor; approving a changed descriptor replaces the old reviewed hash. Revoke is available for an approved or changed approval. Reject/ignore is a menu-local status for the current owner session; it does not write a vault approval record. The menu pins the reviewed candidate and checks it again before confirmation. (Implemented in `internal/ownertui/model.go` and `internal/ownertui/internal/approvals/status.go`, `controller.go`.)

Approve and revoke writes use the owner backend. Local calls the keeper manager's composite approval operation; Remote sends `approve_application` or `revoke_application` through the owner protocol to that same keeper operation. The approvals menu works the same over the local and remote owner channel, with approval records carried to the authenticated owner client as owner-channel metadata (name, path, hash and, if present, the route). Before an approval write, the keeper re-derives the descriptor fingerprint itself from the submitted canonical application path, using the discovery bounded, no-link descriptor verifier; it refuses a mismatch or invalid path. Each approval mutation first prunes old approval snapshots to retain at most the newest 9, takes a snapshot of the last saved encrypted vault ciphertext, then applies and saves the mutation—so the new snapshot is made before that approval write and at most 10 snapshot files are retained. A changed reviewed application receives the fixed message `the reviewed application changed — re-open the approvals menu`; a stale owner revision receives `owner state changed — reopen and retry`. These errors are mapped through the Remote reply codes as well as Local errors. (Implemented in `internal/ownerbackend/local.go`, `remote.go`; `internal/ownerdispatch/dispatch.go`; `internal/ownerservice/service.go`; `internal/application/discovery/verifier.go`; `internal/ownerdb/manager.go`; `internal/vault/internal/session/session.go`; `internal/ownertui/internal/approvals/controller.go`; `internal/ownerrpc/snapshot.go`.)

The owner protocol uses version 2. A version mismatch is refused during the initial Hello authentication, before owner operations proceed. Interactive startup deliberately reports only this fixed generic message: `Owner control could not be opened. The keeper may run a different ssjack protocol version, vault credentials may be invalid, or the owner connection/setup may be unavailable. Restart keeper and client from the same build; verify vault credentials and owner-channel setup.` (Implemented in `internal/ownerpacket/codec.go`, `client.go`, and `cmd/ssjack/internal/shell/interactive.go`.) Noninteractive operation does not present this owner menu. A flag alone is not authorization.

### 6. Tests and acceptance criteria

Build on current descriptor fixtures and strict rejection tests (`internal/application/descriptor_test.go:33-84,145-243`), Unix symlink techniques (`internal/application/descriptor_unix_test.go`), CLI registration setup tests and pre-credential hook (`cmd/ssjack/internal/cli/main_test.go:448-541,543-574`), admission/list tests (`internal/application/admission_test.go:133-203`), and helper-process/app-list tests (`internal/application/application_test.go:106-152`). Add tests, do not relax existing assertions:

- Scanner includes root descriptor and immediate child descriptors, excludes grandchildren, sorts normalized paths deterministically, observes ignore basenames, examines no more than 256 depth-1 directory entries (root descriptor check separately, fixed), accepts no more than 16 valid candidates, detects collisions, deduplicates canonical dirs, and never traverses symlink/junction/reparse candidates (links are rejected, not skipped as candidate directories). Add platform-appropriate symlink and Windows junction/reparse tests. For either entry-count or valid-candidate-count overflow, assert overflow is reported, no arbitrary truncation/selection occurs, and no discovered approved app from the partial scan activates. Assert that a directory with more than 16 rejectable children prints exactly 16 rejection diagnostics plus one summary line, never one line per rejection. Bound every descriptor read by the existing 16 KiB per-file limit.
- A planted valid descriptor appears only as a candidate: before approval it is absent from `app_list`, cannot be routed or launched, and its fixture executable is never run. No discovery operation executes code. With no approved discovered apps, registration and `app_list` behavior remains exactly current; default scanning adds candidate status only.
- Approval persistence, folder identity/hash matching, revoke, malformed records, restart/load, and vault schema compatibility. Assert that matching uses canonical-JSON fingerprints and that whitespace- or line-ending-only edits do not invalidate approval. Re-check scanned directory identity before parsing the captured buffer; assert a path/hash mismatch or failed identity check fails closed and prevents registration. Include OS-specific handle/race tests and document platform semantics. A canonical-JSON descriptor change invalidates approval and prevents both old and changed config from launching until reapproval. File-based descriptor route fields are rejected as unknown; routes are owner-only.
- Startup pre-unlock tests assert bounded candidate parsing/reporting can occur without invoking credential hooks, while approval loading/mutation occurs only after unlock and explicit confirmation. Invalid candidates report safe reason and remain disabled.
- Global route behavior remains identical, including that legacy `--app-route` requires at least one explicit `--app`; approved discovered apps alone do not satisfy it. Per-app bindings validate same regexes, reject unknown/duplicate names and malformed routes, and assert precedence is per-invocation `--app-route-for` > approval-record route for approved discovered applications > legacy/global `--app-route` fallback > no route; the global fallback also covers discovered approved apps without a higher-priority route. Reject unknown apps and duplicate invocation flags. Assert unapproved/rejected candidates do not collide with or block explicit registrations; approved discovered/explicit name collisions fail closed for collision activation and never select by order. Combined discovered-approved and explicit `--app` enabled registrations, deduplicated by canonical directory, never exceed `MaxApplications` (16); overflow is refused/reported, never truncated or chosen by order.
- Compatibility acceptance: old `--app`, old global route, no deprecations, existing profile behavior, no implicit discovery activation, and exact current registration/`app_list` behavior when there are no approved discovered apps (the only default behavior change is additive candidate status).

## Implementation plan (separate, CI-verified slices; historical status)

1. **Scanner only:** implement bounded root/depth-1 candidate enumeration, ignore list, normalization, ordering, deduplication and safe rejection reasons. Add scanner-only tests. Do not feed candidates into registration or change `app_list`; default candidate status is additive only.
2. **Vault approval model — implemented:** encrypted owner approval records, explicit approval/revoke APIs and backward-compatible vault storage. The record contains name, canonical path, fingerprint and optional owner route, not a persisted native folder identity.
3. **Startup integration:** report candidates by default, load/compare approvals after unlock, fail closed on changed or invalid pins, and register only approved entries while enforcing the combined 16-registration runtime cap. Add no-launch/pre-unlock tests and candidate status UX.
4. **Per-app routes:** add encrypted owner route config, validation and precedence; add nonconflicting `--app-route-for` and startup parsing/tests. Preserve `--app-route` global semantics.
5. **Owner TUI approval flow — implemented:** explicit approve/reject/revoke/change-review workflow. The per-app route/help material in this historical plan remains separately described above; no claim here that it is part of the approval menu.

## Open questions (proposed defaults)

1. **When scan?** Default: bounded candidate enumeration/reporting on startup, never activation; omit `--discover` because scanning is default and the flag would be redundant. A CLI flag alone is insufficient protection and is not recommended as the sole authorization boundary.
2. **Approval store?** Implemented: approval records are stored in the encrypted vault as owner-side data; the record binds canonical path and descriptor fingerprint and carries an optional owner route, not native folder identity.
3. **Identity portability?** Default: bind native stable directory identity plus canonical path and exact descriptor hash; moved/replaced folder requires review/reapproval rather than silently transferring approval.
4. **Scan/resource limits?** Default: examine at most 256 depth-1 directory entries (root descriptor check separate and fixed) and accept at most 16 valid candidates. Report at most 16 rejection diagnostics, followed by one summary for additional rejections. Descriptor reads remain bounded by the existing 16 KiB per-file limit. Exceeding either entry or valid-candidate count reports overflow and refuses discovery activation for the scan—no truncation, arbitrary selection, partial scan, or discovered approved app activation. Independently, enabled runtime registrations across discovered-approved plus explicit `--app` entries, deduplicated by canonical directory, must not exceed `MaxApplications` (16); report/refuse overflow rather than truncate or pick by order. Explicit `--app` behavior remains unchanged when used without discovered approvals; legacy `--app-route` continues to require at least one explicit `--app`.
5. **Global route and per-app route?** Default: per-app owner binding wins; old global CLI route remains fallback for all apps; no automatic conversion to per-app bindings.
